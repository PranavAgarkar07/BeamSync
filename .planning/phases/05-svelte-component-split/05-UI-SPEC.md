# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Purpose:** Centralize `window.runtime.*` access behind a Svelte store so no component imports `window.runtime` directly (ROADMAP 5.1, PITFALLS 3a). Must be created before any component extraction.

- Writable stores bound to Wails methods (read-only from components): none currently wired — store wraps the runtime calls below.

**Props:** none (JS module).
**Events:** none.
**Design-system primitives:** none.
**Contract rule:** Every extracted component that needs a Wails call imports `wails.js`, never `window.go.main.App` or `../wailsjs/...` directly.

## Style Ownership Rules

Where CSS lives after the split. Goal: render-identical output; tokens.css remains the single source of truth; no color/font/shadow/spacing re-hardcoding.

### 1. What stays in `app.css` (global, untouched)
- `@import './design-system/tokens.css';` (line 9) — the ONE token import for the whole app. Components must NOT re-import tokens.css.
- Global resets: `*, *::before, *::after box-sizing` (line 12); `html, body` (lines 16-30); `#app` root layout (lines 33-39).
- Typography resets: `h1-h6` (lines 42-47), `p` (lines 49-52 — note undefined `--nb-leading-relaxed`, see Deviations), `button` (lines 55-62).
- Custom scrollbar (lines 65-79).
- `.toast-rack`, `.toast`, `.toast--info/--success/--warn/--error`, `toast-in`/`toast-out` keyframes (lines 82-117) — owned by ToastManager markup but styles remain global in app.css.
- `.update-banner` + `slide-down` keyframes (lines 120-156).

### 2. What moves into each extracted component's own `<style>` (Svelte-scoped)
- `App.svelte` local style block (lines 1409-2232) is dismantled; each class travels with the component that owns its markup:
  - `.app-dropzone`, `.drop-overlay`, `.drop-overlay--visible` → stay in `App.svelte` shell (drag-and-drop remains in shell per PITFALLS 3c).
  - `.progress-float` + children → `ProgressOverlay.svelte`.
  - `.receive-layout`, `.receive-standby`, `.receive-active`, `.home-card*`, `.qr-wrapper`, `.qr-code`, `.instructions-list`, `.url-group`, `.save-path-row`, `.ready-banner`, `.files-panel`, `.empty-state`, `.file-item`, `.sender-dialog*`, `.send-split`, `.send-sidebar`, `.send-main`, `.about-layout`, `.about-card*`, `.developer-card*` → respective `ReceiveView`/`SendView`/`SettingsView`/`AboutView`.
  - `.transfer-request-modal`, modal backdrop → `TransferRequestModal.svelte`.
  - `.toast` markup moves to `ToastManager.svelte` but its styles remain in app.css (global class).

### 3. What must come from tokens.css (never re-hardcode)
All colors (`--nb-*`), fonts (`--nb-font-*`), weights (`--nb-fw-*`), sizes (`--nb-text-*`), spacing (`--nb-space-*`), borders (`--nb-border`, `--nb-border-lg`), shadows (`--nb-shadow-*`), radius (`--nb-radius`, `--nb-radius-chip`), z-index (`--nb-z-*`), transitions (`--nb-transition`). Components use `var(--nb-*)` only. Dark-mode values come automatically via the same token names on `:root.dark` / `prefers-color-scheme: dark`.

### 4. Svelte scoping semantics change (critical)
- `App.svelte` `<style>` is currently component-scoped to `#app`/App markup but many classes (`.app-dropzone`, `.drop-overlay`, `.progress-float`) target elements that will live in child components. After split, classes must be defined in the component that renders the markup so Svelte's scoped class hashing applies correctly.
- Global classes defined in `tokens.css`/`.nb-btn`, `.nb-card`, `.nb-input`, `.nb-badge`, `.nb-mono` are NOT scoped (tokens.css is imported via `@import` in app.css, outside any component `<style>`). These remain available to all components without re-declaration.
- Cross-component classes (e.g., `.nb-btn` used inside multiple views) must NOT be copied into each component's `<style>`; use the global token-based class. Deviations: `DeviceCard.svelte`, `TransferProgressBar.svelte`, `DesignSystemShowcase.svelte` re-declare `.nb-badge`/`.nb-btn` locally — these local copies must not diverge from tokens.css.
- Dynamic inline `style="..."` attributes (App.svelte lines 905-936 modal inline styles, 1205-1212 theme bindings, 1390-1397 progress bar) are allowed to remain where values are dynamic (computed at runtime). Static inline styles (fixed px/rem colors) must be converted to token-based classes.
- No new colors, fonts, shadows, or spacing values may be introduced in any component `<style>`. If a needed value isn't a token, it's a deviation to be logged and either added to tokens.css or normalized to an existing token.

### 5. Verification of style ownership
After split: `rg "var(--nb" desktop/frontend/src/` — every color/font/spacing/shadow must be a var. `rg "#[0-9a-fA-F]{3,8}" desktop/frontend/src/` — hardcoded hex must be limited to logged deviations only (speed colors `#ffb000`/`#00ff00`/`#ff6b6b`, neon `#00e676`, `00B87C`/`00a060` fallbacks).
